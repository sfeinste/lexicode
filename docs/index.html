Lexicode

Field manual · edition 1
Self-hosted agent workspace
One binary · SQLite · Docker

The tickets, the docs, the agents, the triggers and the run logs are one thing. You run it on your own box.

Point it at a GitHub repository, write tickets and a roster of agents, and wire the output of one agent into the input of the next. Agents work in disposable Docker containers running Claude Code and hand back a pull request or a wiki page. A ticket can travel from written to reviewed PR waiting for you without anyone touching a keyboard — and every step stays visible and interruptible.

The thesis in one line: the scarce resource is not agent capability, it is human attention. Everything in this manual is downstream of that.

Ticket ──delegate──▶ Agent run ──▶ PR opened (human or agent) (container) Wiki page ▲ Question ──▶ NEEDS YOU │ │ └── Trigger ◀── GitHub event ◀────┘ Human merges. Always.

Section 01 — the board

Columns you rename. Categories the automations key off.

Every column carries a fixed category — backlog · ready · running · review · done · canceled — and triggers, rollups and automations read the category, never the name. Renaming “In progress” to “Cooking” breaks nothing. A ticket has a human assignee who is accountable and, optionally, an agent delegate doing the work; they are two fields and never one. Dragging a card never starts a run.

Section 02 — a run in flight

A transcript you can read, and an answer box where the question is.

Runs happen in real containers: read-only rootfs, non-root, per-run credentials, a provisioning checklist instead of a spinner. When an agent needs a human it does not fail and it does not guess — it parks, and the question appears in the step detail with the options it drafted. Your answer goes straight back into the running session.

Steer. Send a message mid-run; it is applied after the current step, never mid-tool-call.

Stop. A stopped run still leaves its artifact — a failed run is evidence, not a void.

Take over. Park the agent and pick the branch up yourself, with a note in the record.

Four flavours. Needs input, plan approval, review ready, failed — never one “waiting” badge.

Section 03 — triggers & loop protection

Replay the rule against real history before you turn it on.

The editor is generated from the event catalog, so any event source registered in the binary is expressible without a new screen. Before you enable a rule, backtest it: the server replays your draft against the project's stored events and reports what it would have done. Nothing executes.

Every automation product either bans cascades entirely or discovers them through the billing statement. This one shows you the cycle you built. Design brief §4

Section 04 — the wiki

Docs that are scoped, owned, and dated to expire.

A page that steers machines and has been stale for six months is not an annoyance, it is a live defect. Every page carries an owner, a verified_until date and a scope: manual, path- or keyword-matched, or always — which joins every run's context and spends the project's token budget. When a page expires it is demoted automatically, and the meter says so.

Section 05 — agents

Guidance is prose. Enforcement has a lock on it.

A directive or a wiki page steers an agent. A tool permission and a container network policy constrain it — checked in the runtime and the forge adapter, never written as prompt text. The two are drawn differently on purpose, because a person who confuses them gets badly surprised exactly once and then stops trusting the product.

No merge path. Not a permission that is off — an absent capability. The forge port has no merge method.

No self-approval. Review submission rejects APPROVE unconditionally.

No protected force-push. Refused in the adapter, with an audit row.

Per-run credentials. Scoped to the run, revoked when the container dies.

Section 06 — the inbox

One list. Four reasons. Each with the action that clears it.

“Waiting” is never one state. A question is not a failure; a failure is not a review. Each row names its reason in words, carries the single action that resolves it, and disappears when you take it.

Section 07 — specification

What is in the binary.

Measured on an Apple Silicon laptop, Docker 29.7.2, by the acceptance script
PropertyValueNotes
Distributionone static binaryDashboard, orchestrator, GitHub poller, trigger engine, MCP server
StateSQLite in your data dirNothing leaves the machine except calls to GitHub and the model
SandboxDocker, read-only rootfsNon-root, per-run credentials, egress policy: none / allowlist / open
Connect repo → run in flight0.55 sTo the run reaching running: container up, cloned, agent started
Whole eight-step chain42 sTicket → PR → review → address → CI failure → re-review → loop stopped at depth 3
Loop protection5 layers, on by defaultActor suppression, debounce, cancel-in-progress, depth limit, budget ceiling
Mergehuman onlyNo setting turns this off

Read the timings honestly: they measure the product's share of each goal, not a human's. The agent in the acceptance run is a scripted stand-in working through real seams — real git, the real MCP server, the real forge adapter — so the durations are floor values for the orchestration, not estimates of a thinking agent's work.

Section 08 — installation

Three commands, then a login screen.

# 1. install (see the install guide for a real release host) $ make release && LEXICODE_BASE_URL="file://$PWD/dist" sh scripts/install.sh # 2. check the machine — Docker, ports, disk, credentials $ lexicode doctor # 3. run it $ lexicode serve → http://127.0.0.1:7717 # or explore a populated workspace first: 11 tickets, 2 agents, # 3 runs (one parked on a question), a trigger with history $ lexicode serve --demo --data-dir ~/.lexicode-demo

Then

Create the owner account on the first screen, paste a claude setup-token into Settings → Credentials, connect a repository, write a ticket, and press D to delegate it.
